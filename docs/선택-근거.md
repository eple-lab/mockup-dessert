## 3. 후보 비교

| 기준 | Next.js (App Router) | React + Vite | 순수 HTML·JavaScript |
|---|---|---|---|

| 학습 부담 | 높음. 서버·클라이언트 컴포넌트, 라우팅 규칙을 익혀야 함 | 중간. React 컴포넌트와 상태만 익히면 됨 | 낮음. 이미 배운 내용 |
| 생태계 | 넓음. React 생태계 + 라우팅·API·배포 기능 내장 | 넓음. 라우터·폼 등은 따로 골라 추가 | 좁음. 반복·상태 관리를 직접 구현 |
| 인력·자료 | 많음. 공식 문서와 사례 풍부 | 많음 | 많지만 구조가 프로젝트마다 제각각 |
| 장기 유지보수 | 업데이트가 잦아 버전 대응 필요. 대신 API·서버 기능을 한 프로젝트에서 관리 | 안정적. 서버는 별도 프로젝트 필요 | 화면이 늘면 갱신 코드가 여러 곳에 흩어져 관리 부담이 커짐 |
| 트레이드오프 | 목록만 만들기엔 과하지만, 상품 상세를 HTML로 미리 만들 수 있고 목업 API도 같은 곳에 둘 수 있음 | 가볍지만 검색 노출용 렌더링과 API 서버를 따로 검토해야 함 | 가장 가볍지만 등록·수정·필터가 늘수록 반복 코드가 커짐 |

## 4. 채택·기각 이유

### 채택: Next.js

- 1순위 기준(생태계): React를 그대로 쓰므로 React 자료와 예제를 참고할 수 있다.
- 2순위 기준(트레이드오프): 상품 상세 페이지를 서버에서 HTML로 만들 수 있어 공개 상품 페이지로 확장하기 좋다. 등록·수정·삭제용 목업 API(Route Handler)도 같은 프로젝트에 두고, 나중에 DB로 바꿀 때 `src/lib/products.ts`만 고치면 된다.
- 감수한 부담: 처음 익힐 개념이 많고, 정적 배포(GitHub Pages)를 위해 설정을 따로 나눠야 했다.

### 기각: React + Vite

목업 목록 화면에는 충분하지만, 검색 노출을 위한 렌더링과 등록·수정·삭제용 API 서버를 따로 구성해야 한다. 공개 상품 페이지와 백엔드까지 같은 도구로 확장할 계획이라 이번에는 채택하지 않았다.

### 기각: 순수 HTML·JavaScript

카드 반복은 함수로 충분히 만들 수 있다. 하지만 분류 필터에 따라 목록과 결과 수를 함께 갱신하고, 등록·수정 폼과 화면 이동이 늘어날수록 갱신 코드를 직접 연결해야 할 곳이 많아진다. 화면 4개와 CRUD가 있는 이번 범위에서는 관리 부담이 크다고 판단했다.

## 5. 세부 결정

| 결정 | 선택 | 이유 |
|---|---|---|
| 언어 | TypeScript | 상품 필드의 자료형(가격은 숫자, 품절은 불리언)을 코드에서 바로 확인 |
| 스타일 | Tailwind CSS | Next.js 설치 시 함께 설정되고 빠르게 화면을 꾸밀 수 있음 |
| 상품 데이터 | `data/products.json` 별도 폴더 | 데이터를 화면 코드에서 분리해 한 곳에서 수정·확인 |
| 등록·수정·삭제 저장 | JSON 파일에 직접 저장 | 저장 결과를 파일로 바로 확인할 수 있음. 대신 로컬 전용 |
| 목업 상품 수 | 8개 | 분류 5개, 품절 2개, 이미지 없음 2개, 긴 이름 1개를 모두 담기 위해 |
| 추가 필드 | `description`, `createdAt`, `updatedAt` | 상세 화면 설명과 관리 이력 표시 |
| 배포 | GitHub Pages, 보기 전용 | 무료 정적 호스팅이라 서버 기능(파일 저장)이 없음. 목록·상세만 공개 |
