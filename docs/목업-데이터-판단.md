# 목업 데이터 필요 여부 판단 — 달콤공방 수제 디저트 쇼핑몰

> 작성일: 2026-10-29 · 관련 문서: [PRD.md](./PRD.md), [선택-근거.md](./선택-근거.md)

## 결론

**목업 데이터가 필요하다.** 실제 상품을 저장할 서버와 데이터베이스가 아직 없지만, 화면 4개와 등록·수정·삭제 동작을 먼저 만들고 확인해야 하기 때문이다.

## 근거가 된 화면·요구사항

| PRD 항목 | 목업 데이터가 필요한 이유 |
|---|---|
| U1 상품 목록 | 카드에 표시할 이름·가격·분류·이미지 값이 있어야 화면을 확인할 수 있다 |
| U2 품절 구분 | `soldOut: true`인 상품이 있어야 품절 표시를 확인할 수 있다 |
| U5 분류 필터 | 분류가 여러 개 섞여 있어야 목록과 결과 수가 함께 바뀌는지 확인할 수 있다 |
| A1~A3 등록·수정·삭제 | 백엔드 없이도 저장 결과를 확인할 곳이 필요하다 → 목업 API가 JSON 파일에 저장 |

## 데이터 항목

`data/products.json`, JSON 배열, 상품 8개.

| 필드 | 자료형 | 확인할 점 |
|---|---|---|
| `id` | 숫자 | 중복 없음, 목록의 고유 식별자 |
| `name` | 문자열 | 긴 이름 포함 |
| `price` | 숫자 | `"3,500원"` 같은 문자열이 아니라 원 단위 숫자 |
| `category` | 문자열 | 케이크 · 구움과자 · 마카롱 · 쿠키 · 타르트 |
| `image` | 문자열 | public 기준 경로, 빈 문자열 포함 |
| `soldOut` | 불리언 | `"false"` 같은 문자열이 아닌 `true` / `false` |
| `description` | 문자열 | 상세 화면 설명 |
| `createdAt`, `updatedAt` | 문자열 | ISO 8601 날짜 |

## 목업에 일부러 넣은 확인 상황

데이터에 아래 상황을 일부러 넣어 두고, 화면이 의도대로 나오는지 확인한다.

| 상황 | 데이터 | 기대하는 화면 |
|---|---|---|
| 품절 | 2번 초콜릿 케이크, 5번 바닐라 마카롱 | '품절' 표시, 흐린 이미지, 가격 취소선 |
| 이미지 없음 | 4번 휘낭시에, 8번 얼그레이 쿠키 (`image: ""`) | '이미지 없음' 영역, 카드 크기는 다른 카드와 같음 |
| 긴 상품명 | 7번 타르트 (40자 이상) | 카드에서는 두 줄 후 말줄임, 상세에서는 전체 |
| 빈 목록 | 파일 내용을 `[]`로 바꿔서 확인 | "등록된 상품이 없습니다." |
| 빈 분류 | 상품을 지워 한 분류를 비워서 확인 | "'분류' 분류에는 아직 상품이 없습니다." |

## 목업으로 확인하지 못하는 것

목업은 화면 표시와 동작을 확인하기 위한 것이다. 아래는 실제 서버를 연결한 뒤 따로 확인해야 한다.

- 여러 사람이 동시에 수정할 때의 저장 결과
- 운영자만 등록·삭제할 수 있는 권한 확인
- 느린 응답, 서버 연결 실패, 서버 오류(500) 처리
- 배포된 사이트에서의 저장 (지금은 로컬에서만 파일에 저장됨)

## 실제 API로 바꿀 때 계획

1. 응답 형식을 목업과 같게 맞춘다: 객체로 감싸지 않은 JSON 배열, 같은 필드 이름과 자료형.
2. `src/lib/products.ts`의 파일 읽기·쓰기를 데이터베이스 조회·저장으로 바꾼다. 화면 컴포넌트는 그대로 둔다.
3. 로딩("불러오는 중..."), 오류 안내와 다시 시도 버튼, 빈 목록 상태를 함께 확인한다.
4. 정상 목록, 빈 목록, 느린 응답, 실패 응답을 각각 확인한다.
